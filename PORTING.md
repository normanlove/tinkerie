# Porting Tinkerie

Tinkerie is one Go module (`tinkerie`) using only the standard library, with no cgo. Everything builds for any Go target:

```
GOOS=linux  GOARCH=arm64 go build -o tinkerie .      e.g. a Raspberry Pi 5
GOOS=darwin GOARCH=arm64 go build -o tinkerie .      Apple silicon Macs
```

The launcher and most app logic already run everywhere. What's Windows-only is each app's hardware access (serial, USB, Bluetooth, camera) and, for Meterie, its window. Those parts are behind build tags, with stub files for other systems to fill in.

## Layout

```
main.go              dispatcher: no arguments -> launcher; --app NAME -> that app
launcher/            the launcher (local web page in a Chromium "app" window)
  launcher.go        app list, /api/apps, /api/launch, /api/live; quits when its window closes
  window_*.go        opening the window and detaching started apps, per OS
  web/               the page and the app icons
apps/<name>/         one package per app; Main() is the app's old main()
shared/serialport/   serial ports on Linux, Raspberry Pi and macOS (pure Go, no cgo)
shared/usb/          raw USB on Linux and Raspberry Pi through usbfs (pure Go, no libusb)
shared/appwindow/    opens an app's page as a browser app window on Linux and macOS
shared/xz, zstd/     .xz and .zst decoders for Flashie's image writer (zstd is Go's own internal/zstd, BSD licence)
shared/fat, exfat/   FAT16/FAT32 reading, editing and formatting; exFAT formatting (Flashie)
shared/udf/          lists the files in a UDF disc image (Windows installer ISOs)
shared/teach.js      teaching mode for the web-based apps (a copy is in each app's web folder)
tools/mkicon         draws the Tinkerie icon (build/tinkerie.ico, launcher/web/tinkerie.png)
tools/mksyso         Windows resource: icon, DPI-aware manifest, version info
rsrc_windows_amd64.syso   generated by tools/mksyso and linked into Tinkerie.exe
```

Each app runs in its own process (`Tinkerie --app NAME`), so apps never share global state. Adding an app means adding a package with a `Main()`, plus one line in `main.go` (`mains`) and one in `launcher/launcher.go` (`Apps`). `main_test.go` checks the two lists match.

## Where each app stands off Windows

`*_windows.go` files are the Windows implementation. The matching `*_other.go` files build on every other system.

| App | Runs on Linux/macOS today | Windows-only, to port |
|---|---|---|
| **Wirie** | Everything (web UI, opens in Chromium or the default browser) | none |
| **Makie** | Everything (web UI, geometry engine) | `assoc_windows.go`: "Open with" registration (optional) |
| **Tunie** | Everything; serial opens `/dev/tty*` directly | none |
| **Scopie** | Everything on Linux and Pi (`usb_linux.go` uses `shared/usb`); on Mac, demo, network/SCPI scopes and CSV files | USB scopes on Mac (needs IOKit) |
| **Flashie** | Everything: serial boards, Pico drives (`platform_unix.go`) and image writing (`disks_*.go`) | none |
| **Probie** | Serial monitor everywhere; logic analyser on Linux and Pi (`usb_linux.go`) | Logic analyser on Mac (`usb_darwin.go` explains) |
| **Meterie** | Its window (`web_front.go`, see below) and USB-serial meters (`platform_unix.go`) | HID cables (CH9325, CP2110, BU-86X: Linux could use hidraw), Bluetooth LE (Linux: BlueZ over D-Bus), webcam (Linux: V4L2) |

### Meterie's window on Linux and macOS

Meterie draws its whole interface itself, the same on every system. On Windows it shows the frames in a Win32 window. On Linux and macOS, `web_front.go` serves them to a browser app window: changed 64×64 tiles go over a local long-poll (deflate-compressed), and mouse and keys come back. Text is composited into Meterie's own frames from glyphs the window renders with the embedded fonts (`web/fonts`: Inter and DejaVu Sans Mono subsets; `metrics.json` has their exact advance widths, so measuring matches drawing). Icons are line drawings in `web/icons.js`. `METERIE_FRONT_STATS=1` logs frame rate and timings.

### Hardware

Serial ports on Linux, Pi and macOS go through `shared/serialport`. It sets ports up with termios ioctls (any baud rate: `termios2` on Linux, `IOSSIOSPEED` on macOS), reads through Go's runtime poller, and lists ports with USB IDs from sysfs (Linux) or `ioreg` (macOS). Its tests run on Linux pseudo-terminals. Flashie's `TestESP32FlashOverRealSerial` flashes a simulated ESP32 through it. Raw USB on Linux and Pi goes through `shared/usb` (usbfs ioctls, with queued URBs for streaming; `abi_linux_test.go` checks every ioctl number and struct layout against the kernel headers). `build/install-usb.sh` adds a udev rule so normal users may open the supported devices. macOS USB needs IOKit, which normally means cgo, so it's not done.

## Ports

Each app serves its window from its own local port (127.0.0.1 only). They must not overlap:

| App | Port | If it's busy |
|---|---|---|
| Makie | 47811 | asks the copy already running to open a window, else any free port |
| Wirie | 47820 | the same |
| Tunie | 47821 | the same |
| Probie | 47822 | the same |
| Codie | 47824 | the same as Makie |
| Meterie | 47823 (suite link, for other apps to read the meter) | any free port, written to `%APPDATA%\nrmluvdev\suite\meterie.json` |
| Scopie | 47831 | the same as Makie |
| Flashie, launcher | any free port | |

A fallback must never count up to the next port, because that's another app's.

## Image writer (Flashie's "Write image" tab)

Like Raspberry Pi Imager: pick an OS from Raspberry Pi's official catalogue (`os_list_imagingutility_v4.json`, the list Imager uses) or your own file, pick a removable drive, write, check.

- `imgsrc.go` opens .img/.iso as they are, or packed in .xz, .zst, .gz, .bz2 or .zip, recognised by their first bytes. `.xz` is unpacked by `shared/xz`, a pure-Go xz/LZMA2 decoder (about 100 MB/s; tests compare it with the real `xz` tool, including damaged files). `.zst` is unpacked by `shared/zstd`, Go's own internal decoder copied in, with its 8 MiB window cap raised (to 1 GiB, 256 MiB on 32-bit) so files packed at high levels or with `--long` work; its test files were made by the real zstd library (`testdata/make.py`).
- `imager.go` fetches the catalogue (a copy is kept for offline use), downloads images into the cache with resume and SHA-256 checks, and runs jobs.
- `imgwrite.go` is the writer for every platform. It blanks the start (and the old backup partition table at the end), writes everything else, then writes the first block last, so a half-written drive never looks bootable. It hashes what it writes, compares with the catalogue's `extract_sha256`, and reads the drive back to check it.
- Writing a whole drive needs administrator rights, so Flashie relaunches itself as a helper (`tinkerie --app flashie --img-helper URL TOKEN`): `sudo -n`, else `pkexec` on Linux and Pi; `osascript … with administrator privileges` on macOS; a UAC prompt (`ShellExecute runas`) on Windows. The helper fetches its one job with a one-off token and posts progress back. If Flashie may already open the drive (root, or in the `disk` group) it writes in-process.
- `disks_linux.go`: drives from `/sys/block` (USB, SD card readers, removable), never the disks behind `/`, `/boot`, `/boot/firmware`, `/usr`, `/var`, `/home` or swap (partitions, LVM and LUKS are followed). Writes with `O_EXCL|O_DIRECT`.
- `disks_darwin.go`: `diskutil list -plist physical`, excluding internal disks and the boot disk; writes `/dev/rdiskN` after `diskutil unmountDisk`.
- `disks_windows.go`: `\\.\PhysicalDriveN` with bus type USB/SD/MMC (or removable media), never the disk holding Windows; locks and dismounts its volumes, writes unbuffered.
- `FLASHIE_IMG_TESTDISK=/path/file:SIZE_MB` adds a pretend drive backed by a file, for trying it without a card. `imager_test.go` writes every format to one, and runs catalogue → resumed download → helper → write end to end.
- `custom.go`: OS customisation like Pi Imager's (hostname, user and password, Wi-Fi, SSH with password or keys, time zone, keyboard). After writing and checking, Flashie edits the image's FAT boot partition directly through `shared/fat` (no mounting; `pagedev.go` turns the drive's aligned 4 KiB blocks into byte access and checks what it wrote). Images with cloud-init (Raspberry Pi OS Trixie and later, Ubuntu: `user-data`/`meta-data` on the boot partition, or catalogue `init_format` cloudinit*) get `user-data` and `network-config`; older ones (Bookworm, Bullseye) get Imager 1.x's `firstrun.sh` plus `systemd.run=` in `cmdline.txt`, with `/boot/firmware` or `/boot` picked from the image's `issue.txt` date. The login password goes on the card only as a SHA-512 crypt hash; `firstrun.sh` gets the Wi-Fi WPA key, not the password (cloud-init's `network-config` holds the Wi-Fi password, as Imager 2 writes it). Images without a Raspberry Pi boot partition are written unchanged, with a note.
- `imgwin.go`: Windows 10/11 installer ISOs (found by `sources/boot.wim`, `install.wim/esd/swm` and `efi/boot/boot*.efi` in their UDF file system, read by `shared/udf`). They aren't made to be copied raw, so Flashie formats the drive and copies the files, for UEFI PCs: one FAT32 partition (capped at 32 GB) if every file is under 4 GB; otherwise a FAT32 boot partition (everything except `sources\`, plus `sources\boot.wim`) and an exFAT partition (`shared/exfat`) with the whole installer, where Windows Setup finds `install.wim`. MBR partition table, written last. Every file is hashed while copying and read back to check. Legacy BIOS booting isn't supported (no NTFS, no BIOS boot code).
- Linux ISOs are hybrid images and are written as they are. An ISO 9660 image with no MBR or GPT (CD/DVD-only) gets a warning that it may not start from USB.
- Not tested on real hardware yet: customisation on a real Pi, and Windows installers on a real PC. The file systems are checked by the tests' own spec-based checkers (no `fsck`/`mkfs` was available).

## Teaching mode

Wirie, Makie, Tunie, Flashie, Probie and Codie are web pages. Each loads `teach-tips.js` (its explanations) and `teach.js` (the card, shared by all). Edit `shared/teach.js`, then copy it into `apps/{wirie,makie,tunie,probie,codie}/web/` and `apps/flashie/`. Scopie keeps its own help bar (`apps/scopie/web/tips.js`). Meterie draws its own window, so its version is `apps/meterie/teach.go`, and `TestTeachingCoverage` lists any control without an explanation.

## Notes

- Some apps still have their own generator tools (`apps/scopie/tools/mkres`, `apps/tunie/tools/mkres`, `apps/wirie/tools/mkrsrc.go`, `apps/meterie/tools/mksyso`). They write web icons, which is fine, but they also write an `rsrc_windows_amd64.syso` into the app's folder. Delete that file afterwards: only the root `.syso` may be linked, or the build fails with duplicate resources.
- The apps' own READMEs still describe building them as separate programs. In this repository, build from the root instead.
- On Windows the launcher looks for Edge, Chrome or Brave and falls back to the default browser. Elsewhere it tries Chromium-based browsers, then `xdg-open` or `open`.

## Android

`android/` is a small Java app (no libraries) around the same Go program, built for each Android ABI with the NDK (`android/build.sh`) and shipped inside the APK as `lib/<abi>/libtinkerie.so`, so Android lets it run. The Java side:

- runs the launcher (and, through it, every app) as child processes, in a foreground service so long jobs keep going;
- shows each app's page in a WebView window of its own (Recents shows them like desktop windows);
- answers the Go programs on an abstract Unix socket named in `TINKERIE_BRIDGE` (`shared/droid`): open a window, a link or a folder, choose a file, list USB devices, and open one, handing over its file descriptor once the person allows it;
- shows `$HOME/Documents` in the Files app as "Tinkerie" (`DocsProvider`).

On the Go side, `droid.Active()` is true on Android. `shared/usb` lists and opens devices through the bridge (usbfs works the same on the handed-over descriptor), `shared/serialport` drives USB serial adapters over USB (`usbserial.go`: CDC-ACM, CH34x, CP210x, FTDI, PL2303) because apps can't open `/dev/tty*`, and Flashie writes UF2 boards and SD card readers over USB mass storage (`shared/usb/msc.go`). Compiling Arduino code isn't available: arduino-cli's compilers are built for desktop Linux.

`.github/workflows/android.yml` tries each push on Android 5, 10 and 15 emulators (`android/smoke.sh`) and adds the signed APK to each release; signing needs the `ANDROID_KEYSTORE_B64` and `ANDROID_KEYSTORE_PASSWORD` repository secrets.
